Introduction

Jacob is an iteration of Edward, Thinking Machines' web application that assists TM8s in generating their daily checkins. Edward generates checkins primarily from Google Calendar events by extracting scheduled work activities and calculating the corresponding hours rendered. While this workflow is effective for scheduled work, it is limited by the information available in calendar events, which may not fully capture a TM8's daily activities.

Jacob extends Edward by incorporating additional workplace data sources, specifically Google Calendar, Gmail, and Slack, to provide a more comprehensive representation of a user's work activities. These sources are aggregated into a unified activity log, allowing the system to generate more grounded and context-aware daily checkins while reducing the amount of manual work required from TM8s.

Jacob also introduces an AI-assisted workflow through a Custom GPT specifically engineered for daily checkin generation. The AI model follows prompt-engineered instructions, validation rules, and curated knowledge files to generate grounded outputs based solely on retrieved workplace activity. For TM8s belonging to the DataOps team, Jacob supports an additional workflow that applies the DataOps Standard Operating Procedure (SOP) after user confirmation, enabling SOP-compliant checkin generation while preserving the standard workflow for all other users.

For more information, see the Project Proposal.

Use Cases

Jacob extends the existing Edward workflow by introducing AI-assisted checkin generation while preserving Edward's standard calendar-based functionality. Users may continue using Edward to generate calendar-based daily checkins or retrieve a unified activity log from Google Calendar, Gmail, and Slack for use with Jacob. Jacob supports both the general TM8 workflow and a specialized DataOps workflow, while also allowing users to generate checkins for previous dates to assist in completing backlogged submissions.

Non-Functional Requirements

What are the usability requirements?

The primary measure of usability is the application's ability to retrieve workplace activity accurately while providing a simple and familiar workflow for generating daily checkins. Users should be able to navigate the application with minimal effort regardless of whether they choose the Standard Edward workflow or the Jacob AI-assisted workflow.

The user interface should remain consistent with Edward's existing design, allowing existing users to transition naturally to the new features introduced by Jacob. Aggregated activity should be presented in a human-readable format, organized by Calendar, Gmail, and Slack, eliminating the need for users to interpret raw JSON data. Common actions such as generating activity, copying activity logs, and generating checkins should require only a few interactions.

Details:

  • Support selected dates.
  • Display clear loading indicators.
  • Display clipboard confirmation after copying.
  • Use consistent terminology throughout the application.
  • Present activity grouped by Calendar, Gmail, and Slack.
What are the reliability and up-time requirements?

Jacob should continue operating even when one or more workplace connectors are unavailable. Failure to retrieve activity from one service should not prevent activity from being retrieved from the remaining available services. Likewise, if a user declines access to one connector, the application should continue functioning using the remaining authorized data sources.

The AI-assisted workflow should continue generating checkins using whatever workplace activity is successfully retrieved while informing the user of any unavailable sources.

Details:

  • Gracefully handle API failures.
  • Continue processing available activity sources.
  • Preserve generated activity files.
  • Retry failed API requests where appropriate.
What are the safety requirements?

Jacob is intended to assist TM8s in preparing their daily checkins and should not automatically submit generated outputs. Users remain responsible for reviewing generated checkins before submission.

All retrieved workplace activity should remain unmodified and be treated as supporting evidence for AI-assisted generation.

Details:

  • Use read-only APIs.
  • Do not automatically post generated checkins.
  • Require user review before submission.
  • Preserve retrieved workplace activity.
What are the security requirements?

Access to workplace data shall only occur after explicit user authorization. Jacob shall request permission before accessing Google Calendar, Gmail, or Slack and shall only retrieve information necessary for generating daily checkins.

Authentication tokens shall be securely managed using trusted authentication services. When authentication expires, users shall be required to authenticate again before additional workplace data can be accessed.

Details:

  • Firebase Authentication.
  • Google OAuth.
  • Slack OAuth.
  • Read-only permissions.
  • No persistent storage of user credentials.
What are the performance and scalability requirements?

Jacob should retrieve workplace activity and generate summarized activity within an acceptable response time for normal daily use. As additional workplace connectors or larger volumes of activity are introduced, the application should remain responsive without requiring major architectural changes.

The activity aggregation pipeline should support future expansion while maintaining acceptable performance for both current-day and historical activity generation.

Details:

  • Parallel API retrieval.
  • Efficient Dagster orchestration.
  • Modular connector architecture.
  • Support increasing activity volume.
What are the maintainability and upgradability requirements?

Jacob should remain easy to maintain by separating responsibilities across the frontend, backend, data orchestration pipeline, and AI prompting components. Individual API connectors and AI workflows should be independently extensible without requiring major modifications to the rest of the application.

Comprehensive project documentation should support future developers in understanding the system architecture, implementation decisions, and software requirements.

Details:

  • New connectors can be added independently.
  • New TM8 workflows can be introduced.
  • Prompt files remain separate from application code.
  • Maintain modular frontend and backend architecture.
What are the supportability and operability requirements?

The application should provide meaningful feedback whenever failures occur during authentication, API retrieval, or activity generation. Error messages should help users understand what occurred while application logs should assist developers in diagnosing and resolving issues.

Project documentation should provide sufficient information for maintenance, onboarding, and future development.

Details:

  • Display API error messages.
  • Maintain Dagster execution logs.
  • Maintain repository documentation.
  • Maintain ReadySET documentation.
What are the business life-cycle requirements?

Jacob should continue evolving while maintaining compatibility with existing workflows. The application should support future workplace connectors, AI improvements, and additional TM8-specific workflows without requiring significant architectural changes.

Jacob shall support generating activity and checkins for previously selected dates, provided the required workplace data remains available through the connected services.

Details:

  • Support evolving TM8 workflows.
  • Support additional workplace connectors.
  • Support future AI model improvements.
  • Maintain compatibility with Edward.
  • Support retrieval of historical workplace activity through connected APIs.
  • Support additional TM8 specializations beyond DataOps.

Environmental Requirements

What are the system hardware requirements?

Jacob is designed to operate on standard desktop and laptop computers capable of running modern web browsers. The application does not require specialized hardware and may be used on any device that supports modern web technologies and maintains a stable Internet connection for communication with external workplace services.

Since Jacob relies on external APIs to retrieve workplace activity, Internet connectivity is required throughout authentication, activity retrieval, and AI-assisted checkin generation.

Details:

  • Microsoft Windows.
  • macOS.
  • Linux.
  • Modern desktop or laptop computer.
  • Stable Internet connection.
  • Modern web browser.
What are the system software requirements?

Jacob is implemented using modern web technologies to support a modular and maintainable architecture. The frontend is built using React, while the backend is implemented using Node.js. Data orchestration is handled by Dagster, and Firebase Authentication is used to manage user authentication.

These technologies provide a scalable foundation that supports additional workplace connectors and future AI workflows.

Details:

  • React.
  • Node.js.
  • Python.
  • Dagster.
  • Firebase Authentication.
What application program interfaces (APIs) must be provided?

Jacob depends on several external APIs to retrieve workplace activity used during checkin generation. These APIs provide read-only access to user information after explicit authorization and serve as the primary evidence used by the AI-assisted workflow.

Authentication services are also required to securely authorize access to workplace data.

Details:

  • Google Calendar API.
  • Gmail API.
  • Slack API.
  • Google Identity Services.
  • Firebase Authentication.
What are the data import and export requirements?

Jacob imports workplace activity from supported external services and transforms the retrieved information into a unified activity log suitable for AI-assisted processing. The imported activity is preserved in intermediate artifacts before being merged into a single activity representation.

The application exports a human-readable activity summary for user review, a structured activity log for AI consumption, and copy-pastable daily checkins generated by either Edward or Jacob.

Details:

  • Imported Data
    • Google Calendar events.
    • Gmail metadata.
    • Slack workspace messages.
    • Slack workspace channels.
  • Generated Artifacts
    • calendar.json
    • gmail.json
    • slack.json
    • activity.jsonl
  • Exported Data
    • Human-readable activity summary.
    • Copyable activity log.
    • Generated daily checkins.
    • AI-assisted DataOps checkins (when applicable).
